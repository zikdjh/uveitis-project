持久化分析任务队列

PostgreSQL 任务状态、Worker 租约、失败重试、过期回收与幂等完成边界

分析请求不再依赖 Web 进程内临时后台任务。Web 接口只负责建立病例的排队快照和持久任务，实际分析由 Web 后台执行器或独立 Worker 原子领取；进程重启后可以从 PostgreSQL 恢复未完成任务。

任务生命周期

状态含义可执行者转移条件
queued等待领取。任意活跃 Worker原子领取后进入 running。
running已被某个 Worker 领取，持有短租约。仅租约持有者进入结果封口、失败重排、超过次数或租约过期。
finalizing推理已结束，持有者正在写病例并关闭任务。仅原租约持有者写回成功后变为 completed；异常则重排或失败。
completed病例分析结果已写入，任务已关闭。不再执行不可逆；重复触发只返回已完成。
failed不可重试或达到最大尝试次数。不再自动执行需要人工排查后创建新任务。

任务以 f_job_key UUID 作为业务标识，f_id 仅作数据库自增主键。Service、HTTP 后台回调和任务表查询都只使用 f_job_key，不得把整数主键传入业务接口。

租约与重试

  • 默认租约为 300 秒，最大尝试次数为 2；可通过 APP_ANALYSIS_JOB_LEASE_SECONDS 和 APP_ANALYSIS_JOB_MAX_ATTEMPTS 调整。
  • 领取使用 PostgreSQL 行锁与 SKIP LOCKED，并发 Worker 不会同时领取同一任务。
  • 执行前验证 lease_owner 等于当前 Worker 且租约未过期；其他进程即使拿到任务键也只能返回 not_claimed。
  • 推理期间由同一 Worker 按租约三分之一周期续租，长推理不会因为固定 300 秒窗口自动失租；续租、封口和关闭都校验当前持有者。
  • 推理结束后先原子进入 finalizing，再写病例结果；失去租约的旧 Worker 不能封口或覆盖新结果。
  • 暂时性分析异常会写回失败状态并将任务重新排队；达到上限后关闭为 failed。
  • 进程异常退出遗留的过期租约，会在 API 启动和 Worker 轮询时回收并重新排队。

幂等与一致性

病例模型结果与任务状态目前是两个持久化动作，不宣称跨表原子事务。重新执行任务前会检查病例是否已经是 awaiting_review 或 reviewed 且分析结果为 completed；满足时只补写任务完成状态和待复核队列，不重复执行模型。

该处理覆盖“病例已保存、任务尚未关闭”的进程中断窗口。病例保存失败时仍由重试机制收敛；如果模型调用本身产生外部副作用，后续接入真实运行服务时仍需保证该调用可安全重放。

启动方式

cd backend
.\.venv\Scripts\uvicorn.exe app.asgi:app --host 127.0.0.1 --port 8000
.\.venv\Scripts\python.exe -m app.worker

只启动 Web 进程时，分析仍由 Web 后台执行器完成。生产环境建议单独运行 analysis-worker，让 API 与耗时分析分别扩缩容。Docker Compose 已定义该服务并依赖 PostgreSQL、Redis 和模型运行服务。

剩余边界

  • 队列持久化已完成，但真实模型运行服务尚未完成后端业务回写验收。
  • 分析结果与任务状态没有单一数据库事务；当前依靠 finalizing 封口、幂等完成逻辑和重试收敛。后续若引入任务以外的业务副作用，仍需评估共享事务或 outbox。
  • 任务没有独立管理页面；当前通过病例状态、PostgreSQL 任务表和运行日志排查。
  • 任务完成不等于临床验证通过。医生复核仍是强制业务边界。
  • 完整容器启动仍受基础镜像拉取阻塞。默认与隔离端口 Compose 配置均已通过解析，但不能替代真实跨容器验收。
